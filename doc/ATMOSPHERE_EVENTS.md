# Атмосферные события

## Границы системы

`AtmosphereDirector` — отдельный от `ThreatManager` директор несмертельных событий.
Ивенты не требуют реакции или взгляда игрока, не портят доказательства и не управляют
посадкой/выходом из ПК. Игрок может ничего не заметить. Случайный ивент не останавливает
маршрут наблюдаемой цели.

Первый production-ивент: [You Are An Idiot](YOU_ARE_AN_IDIOT.md), в общем пуле
`data/atmosphere/default.tres`. Его окна могут временно перекрывать CCTV, но не меняют
доказательства или ход маршрута; это согласованное исключение по видимости интерфейса.
Старая `[ТЕСТ ПУГАЧКИ]`, принудительный выход из ПК и пятисекундный таймер удалены.
При пустом пуле переход происходит сразу; причина остаётся только в dev-диагностике.
Тестовые обработчики находятся исключительно в `tests/`, исключённых из production.

## Расписание

- После ALARM.sh директор активируется и резервирует два разных подходящих ID
  для переходов офис → магазин и магазин → улица. Выбор взвешенный.
- Общий пул: событие может поддерживать случайный запуск, межсценовый или оба.
  Случайная выборка не расходует зарезервированные ID.
- При переходе неподходящий текущему контексту резерв заменяется свободным подходящим
  событием, без расходования резерва второго перехода.
- Если на границе маршрута уже идёт случайный ивент, он выполняет роль межсценового.
  Неиспользованный резерв этой точки возвращается в общий пул.
- Межсценовый ивент удерживает следующий маршрут до завершения/отмены/таймаута.
  При исчерпанном одноразовом пуле разрешён повтор подходящего события.
  Если кандидатов нет вообще или их setup не удался — переход пропускается с dev-записью.
- Случайные ивенты разрешены во время маршрутов и возвращения к финальному отчёту.
  Начало опроса отменяет активный ивент и запрещает новые.
- Стартовая настройка: лимит 1–2 случайных события, задержка 40–70 секунд
  **подходящего** времени между попытками. Вместе с двумя переходами целевой ритм —
  примерно 3–4 события, не обязательная квота. Нет догоняющих запусков после долгого кадра.
- Каждый ID расходуется при успешном старте, даже если затем отменён. Неудачный setup
  не расходует ID. Ручной dev-запуск и fallback перехода могут обходить одноразовость.

## Условия и угрозы

Новые события запускаются только при питании и в устойчивом контексте:
`computer` либо `walking`. Укрытие, щиток, переход камеры и открытая dev-панель
останавливают новые старты; переход между локациями в это время ждёт.
После запуска смена контекста **не отменяет** событие.

Активная угроза, включая её уход и ремонт отключения, блокирует атмосферу.
Атмосферное событие и ожидающий межсценовый переход блокируют **новые** угрозы
через причины `atmosphere` / `atmosphere_pending`. Уже начавшуюся угрозу они не
останавливают. После угрозы дополнительной атмосферной передышки нет.
Отключение атмосферы не отключает угрозы, и наоборот.

## Добавление контента

1. Создать сцену с корневым `Node` или `Node3D`, использующим наследника
   `scripts/atmosphere/atmosphere_event.gd`.
2. Реализовать контракт:
   - `start(game) -> bool`: подготовка; `false`, если запустить не удалось;
   - `advance(delta)`: логика времени, без ожидания внимания игрока;
   - `finished.emit(outcome)`: нормальное завершение;
   - `ended(outcome)`: идемпотентная очистка звуков, объектов и изменений мира,
     также после частичного setup, отмены, watchdog и выгрузки.
3. Создать ресурс `AtmosphereProfile`: уникальный `id`, `scene`, `enabled`, вес,
   флаги `random_trigger` / `transition_trigger`, контексты `at_computer` / `walking`
   и обязательный конечный `timeout_seconds`.
4. Добавить профиль в `AtmosphereConfig.events` ресурса
   `data/atmosphere/default.tres`. Другой конфиг можно назначить в Inspector на Main
   через `atmosphere_config`.

Каждый запуск создаёт новый экземпляр сцены. Директор владеет его временем и очисткой;
не нужно заводить независимые таймеры, ожидающие input или visibility. Поздние сигналы
старого экземпляра игнорируются. Синхронное завершение из `start()` поддерживается.
Не изменять общие ресурсы конфигурации во время забега.

Контент должен покрывать оба контекста переходов. Маленький/неправильно настроенный
пул может дать повтор или пропуск; директор не будет навечно блокировать прохождение.
Значение веса должно быть положительным, таймаут — конечным и больше нуля.

## Dev

F7 → Atmosphere events: отдельное включение, выбор и запуск ID, завершение, отмена,
сброс задержки. Статус показывает текущий контекст, блокировку, пул, использованные ID,
резервы, лимит случайных событий и последние 12 записей. Те же сведения доступны
в опциональном Debug HUD, без обычных игровых подсказок.

Dev-запуск обходит время, одноразовость и резерв, но не отключённый профиль/директор,
контекст, другой ивент, угрозу, отсутствие питания, опрос и конец забега.

## Проверки

```
godot --headless --path . --script res://tests/atmosphere_smoke.gd
godot --path . --script res://tests/atmosphere_smoke.gd
```

Web: во временной копии проекта назначить main scene
`tests/atmosphere_fixture.tscn`, убрать `tests/*` из исключений Web preset,
импортировать и экспортировать release. Запустить:

```powershell
$env:THREAT_WEB_ROOT = '<каталог Web экспорта>'
$env:THREAT_WEB = '1'
node tools/chat_web_check.mjs
```

Результат проверок публикуется только тестовой сценой (`window.threatTestResult`).
